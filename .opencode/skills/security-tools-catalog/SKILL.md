# Security Tools Catalog

Reference for choosing and using security tools. The structure follows the article *Herramientas
de ciberseguridad y para qué sirve cada una* (Campus Ciberseguridad), but **only open source tools
are allowed in this system**. Tools from the article that are proprietary or paid were replaced
by open source equivalents (see the licensing policy). The DevSecOps part is an addition for
software projects generated by this system.

## Licensing policy (mandatory)

Use only open source tools, with a license approved by the OSI (Apache-2.0, MIT, BSD, GPL, LGPL,
AGPL, MPL) whose full functionality is free. Do not use tools that are paid, freemium with locked
features, trial-only, or source-available with restrictive licenses (SSPL, BUSL, Elastic License).

| Tool from the article | Why it is not allowed | Use instead |
|-----------------------|-----------------------|-------------|
| Burp Suite | Proprietary; the free Community edition is limited and closed source | OWASP ZAP (Apache-2.0), mitmproxy (MIT) |
| IDA Pro | Commercial, paid license | Ghidra (Apache-2.0), Rizin / Cutter (GPL) |
| Splunk | Proprietary; the free tier is limited | Wazuh (GPL-2.0), OpenSearch with Security Analytics (Apache-2.0) |
| Elastic Security | Elastic License / SSPL, not OSI open source | Wazuh, OpenSearch Security Analytics |

Notes:
- **Metasploit**: use only Metasploit Framework (BSD-3-Clause). Metasploit Pro is commercial.
- **Nmap**: free and with public source code, but under the custom Nmap Public Source License
  (not OSI-approved). It is accepted here as an exception; do not use its commercial OEM edition.
- **Semgrep**: use only the open source engine (LGPL-2.1) with rules written by the project or
  with permissively licensed rule sets. Do not use paid Semgrep products.
- Before adopting any tool not listed here, check its license. If it is not open source, do not
  use it and record the decision in `resultEvidence`.

## Ground rules (mandatory)

1. **Containers only.** Run every tool inside a Docker container, following the
   `docker-test-runner` skill (hardened flags, private network, no host mounts except the project
   directory). Never install or run these tools on the host.
2. **Authorized targets only.** The only valid targets are the application under development and
   the throwaway containers created for the current ticket, reachable by name on a private Docker
   network. Never scan the host, the LAN, the internet or any third-party system.
3. **No offensive capabilities in the project.** Exploit modules, payloads and cracked secrets are
   evidence for a report, never project files. Do not commit them.
4. **Least privilege.** Do not use `--privileged`, `--network host`, the Docker socket or the home
   directory. Add only the capabilities a tool really needs (for example `NET_RAW` for Nmap SYN
   scans or packet capture) and only for that container.
5. **Pin images.** Use a fixed tag or digest, never `latest`; record it in `resultEvidence`.
6. **Report, do not exploit further.** Stop at proof of impact, describe the fix, create a ticket.

## Blue Team and monitoring

- **Wireshark**: deep visibility into who talks to whom, with which protocol. Use display filters
  to isolate protocols, IPs, ports or conversations. It does not replace an IDS or a SIEM. In
  containers use its command-line version `tshark`, or capture with `tcpdump` and open the
  `.pcap` as a read-only file.
- **Wazuh / OpenSearch Security Analytics**: centralize logs from servers, applications,
  firewalls and cloud services; correlate events (failed logins followed by a successful one from
  an unusual place), create detection rules, dashboards and alerts. Use them for log-pipeline
  design, not as test targets.
- **Snort / Suricata**: IDS (alert) or IPS (block) driven by rules, looking for scans, exploitation
  attempts and malicious communications. Suricata also parses protocols and writes structured
  JSON (`eve.json`) that integrates with Wazuh and OpenSearch. Run them in a container against a
  `.pcap` file (offline mode) or on the private test network.
- **Typical flow**: Suricata detects suspicious traffic → Wazuh/OpenSearch centralizes the alert →
  the analyst contextualizes it → Wireshark digs into the related traffic.

## Red Team and ethical hacking (authorized targets only)

- **Kali Linux**: an environment, not a tool; it bundles Nmap, Metasploit Framework, Wireshark,
  Hashcat and more. Use the official container image as the single attacker container instead of
  installing each tool, attached to the private network of the ticket. Do not use any proprietary
  tool that may ship in it.
- **Nmap**: map the attack surface. Example against a container of the ticket:
  `nmap -sV app-under-test` (`-sV` tries to identify service versions). Nmap gathers information;
  it does not exploit.
- **Metasploit Framework**: confirm whether a finding is really exploitable, to measure impact and
  prioritize fixes. Use it only against containers created for the ticket and only to prove the
  finding.
- **OWASP ZAP**: intercepting proxy and scanner for HTTP/HTTPS. Run it headless in a container
  (`zap-baseline.py` for passive scans, `zap-api-scan.py` for OpenAPI definitions, `zap-full-scan.py`
  for active scans on the throwaway application). Look for authentication, access-control,
  input-validation and session-management flaws. Its Manual Request Editor and fuzzer cover what
  other tools call Repeater and Intruder.
- **mitmproxy**: command-line proxy (`mitmdump`) to inspect and modify requests and responses,
  useful to script tamper tests against APIs.
- **Typical flow**: Nmap (hosts, ports, services) → ZAP (web application) → Metasploit Framework
  (validate one concrete vulnerability).

## Malware analysis and reverse engineering

- **Static analysis** (understand code without running it): Ghidra (disassembler and decompiler)
  and Rizin/Cutter. Look for file access, process creation, network communication, persistence
  and memory manipulation.
- **Dynamic analysis** (observe behavior): x64dbg (Windows) and GDB (Linux/Unix): breakpoints,
  registers, memory, step-by-step execution.
- Combine both: first the structure, then behavior inside an isolated lab; use Wireshark to see the
  network traffic that the sample generates.
- **Safety**: never execute a suspicious sample on the host. Use a container with
  `--network none` (or a private network with no route out), read-only root filesystem, no
  capabilities, CPU/memory/pids limits. If a sample needs stronger isolation than a container
  gives, stop and create a ticket for a human.

## Password and credential auditing

- **Hashcat**: hash cracking with dictionary, mask, combination and rule attacks; GPU-oriented.
- **John the Ripper** (community edition): many hash formats, automatic format detection,
  dictionary, rules and brute force; very flexible, long-established.
- Purpose: detect weak credential policies in authorized audits, never obtain passwords without
  authorization. Use only hashes generated for the test, never real user data. Never write
  recovered passwords to the repository, logs or `resultEvidence`; report only counts and policy
  recommendations.

## DevSecOps for generated projects (additional tools)

These fit the code produced by this system, are open source and run well in containers:

| Need | Tool (license) | Notes |
|------|----------------|-------|
| Dynamic scan of the running web app | OWASP ZAP baseline scan (Apache-2.0) | Target the app container on the private network |
| Dependency vulnerabilities | `npm audit`, `pip-audit` (Apache-2.0), OSV-Scanner (Apache-2.0), Trivy (Apache-2.0) | Run inside the project's runtime container |
| Container image vulnerabilities and misconfiguration | Trivy, Grype (Apache-2.0) | Scan the images the project builds |
| Static code analysis (SAST) | Semgrep engine (LGPL-2.1) with project rules | Rules for injection, XSS, unsafe deserialization |
| Secrets in code and history | Gitleaks (MIT) | Run before every push to the trunk |
| Dockerfile and IaC checks | Hadolint (GPL-3.0), Trivy config | Run on `Dockerfile` and compose files |

## Running a tool in a container (template)

```bash
NET="$TICKET_ID-net"
docker network create --internal "$NET"          # no route to the outside

# application under test, also on the private network (see docker-test-runner)
# ...

docker run --rm --init --network "$NET" \
  --cap-drop ALL --cap-add NET_RAW \
  --security-opt no-new-privileges --read-only --tmpfs /tmp \
  --pids-limit 256 --memory 1g --cpus 2 \
  <pinned-nmap-image> -sV app-under-test        # example with Nmap

docker network rm "$NET"
```

- Use `--internal` networks so scanners cannot reach anything outside the ticket.
- Mount the project as read-only (`-v "$PROJECT_DIR":/work:ro`) for static analysis; write reports
  to a dedicated directory such as `reports/security/`.
- Remove containers and networks when finished.

## Severity and reporting

Rate each finding with CVSS or Critical / High / Medium / Low, map it to OWASP Top 10 or CWE, and
record: title, affected component, evidence (command, image tag, trimmed output), impact,
recommended fix and a verification step. Critical or high findings become blocker tickets.
